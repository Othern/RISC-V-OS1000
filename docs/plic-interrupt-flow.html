PLIC Interrupt 註冊與處理流程

以本專案的 VirtIO block IRQ 1 與 VirtIO network IRQ 2 為例，說明初始化時如何讓中斷可被送達，以及裝置提出 interrupt request 後，Device、PLIC、CPU 與 driver 之間的完整互動。

PLIC Interrupt 的「註冊」

PLIC 沒有 callback registration API。這裡的「註冊」是 kernel 同時設定 PLIC source、CPU interrupt enable 與軟體 dispatch table，讓指定 IRQ 可以進入正確的 handler。

裝置設定 PLIC 設定 CPU / kernel 設定
1

確認 IRQ ID

IRQ ID 由 machine/platform wiring 決定，不是 VirtIO 規格固定值。

VIRTIO_BLK_IRQ = 1
VIRTIO_NET_IRQ = 2
2

設定 PLIC source

設定 priority，並在目前 hart 的 S-mode enable bitmap 開啟該 IRQ。

priority[irq] = 1;
senable |= 1 << irq;
threshold = 0;
3

設定 CPU trap

設定 trap 入口，允許 supervisor external interrupt，最後開 global interrupt。

stvec = kernel_entry;
sie.SEIE = 1;
sstatus.SIE = 1;
4

建立軟體分派

claim 得到 IRQ ID 後，由 kernel 選擇對應 driver handler。

IRQ 1 -> virtio_blk_irq()
IRQ 2 -> virtio_net_irq()
建議順序：先完成 device queue、PLIC、stvec 與 dispatch 初始化，最後才設定 sstatus.SIE。否則初始化中的 pending IRQ 可能提早進入尚未準備完成的 handler。

三層 Enable 必須同時成立

層級 本專案設定 作用
PLIC source priority > threshold 且 senable[irq] = 1 允許特定外部 IRQ 被送往目前 hart 的 supervisor context。
CPU interrupt type sie.SEIE = 1 允許 supervisor external interrupt 這個類型。
CPU global sstatus.SIE = 1 允許 S-mode 當下接收已啟用的 interrupt。

裝置提出 Interrupt Request 後

點選步驟觀察各角色。一次 supervisor external interrupt 只表示「PLIC 有可服務的來源」，CPU 必須讀 claim register 才知道實際 IRQ ID。

VirtIO Device

完成 descriptor、更新 used ring、設定 VirtIO interrupt status，並拉起 IRQ line。

PLIC

記錄 pending source、比較 priority/threshold，向 CPU 提出 supervisor external interrupt。

CPU + Kernel

進入 trap、claim IRQ、執行 driver handler，最後 complete IRQ。

1 Device → Device 完成工作 例如 RX 收到 frame、TX 送完，或 block request 完成；device 先更新 used ring。
2 Device → PLIC → Device 提出 IRQ request VirtIO MMIO 的 InterruptStatus 設定 used-buffer bit，平台 IRQ line 送入 PLIC source。
3 PLIC → PLIC 選擇可服務來源 只有 enabled、pending，而且 priority 高於 threshold 的來源才有資格通知 CPU。
4 PLIC → CPU → CPU 進入 external interrupt trap scause.interrupt = 1、cause code 為 9；此時尚不知道是 IRQ 1 還是 IRQ 2。
5 CPU ↔ PLIC → 軟體讀取 claim register PLIC 回傳最高優先權 IRQ ID，並由硬體把該 source 標記為 in-service。回傳 0 代表沒有可 claim 的來源。
6 CPU → Device → Driver 處理並 ACK device 讀取 VirtIO InterruptStatus、寫入 InterruptACK，再 drain 對應 used ring。
7 CPU → PLIC → 軟體寫入 complete 將同一 IRQ ID 寫回 claim/complete register，通知 PLIC 此次服務完成，清除 in-service 狀態。
8 PLIC / CPU → 返回或處理下一個 IRQ 若仍有其他 eligible pending source，PLIC 可再次通知 CPU；否則 trap return 回原本執行點。
步驟 1 / 8

Pending、Claimed 與 Completed

PLIC source 狀態

軟體讀 claim 時，PLIC 硬體自動選出 IRQ 並把它視為正在服務；軟體不需額外寫「in-service」flag。

idle → request → pending → claim → in-service → complete → idle

Device completion 狀態

PLIC 只管理 IRQ source，不知道 VirtIO queue 完成了哪些 descriptor。driver 必須另外讀 VirtIO status 與 used ring。

submitted → device → used ring → driver drain → consumed

兩種 Acknowledge 不可互相取代

VirtIO InterruptACK

作用對象是裝置。清除 device 的 interrupt reason，例如 used-buffer completion。若漏掉，裝置可能持續保持 IRQ request。

status = virtio_irq_status(dev);
virtio_irq_ack(dev, status);

PLIC Complete

作用對象是 PLIC。結束 claim 建立的 in-service 狀態。若漏掉，同一來源後續可能無法正常再次被 claim。

irq = plic_claim();
handle_irq(irq);
plic_complete(irq);
正確順序通常是：claim → device handler/ACK → drain completion → PLIC complete。只 complete PLIC 而沒有處理裝置原因，IRQ line 可能仍為 asserted；只 ACK device 而沒有 complete PLIC，控制器仍認為該 IRQ 正在服務。

多個 IRQ 同時發生

PLIC 依 priority 選擇可服務來源；相同 priority 時的 tie-break 由 PLIC 實作規則決定。一次 claim 只回傳一個 IRQ ID，因此 handler 應快速完成，返回後再服務其他 pending IRQ。

情況 PLIC / CPU 行為 Driver 注意事項
IRQ 1、IRQ 2 同時 pending claim 先回傳其中一個 eligible source。 完成第一個後，另一個仍可再次觸發 external interrupt。
一個 IRQ 對應多個 completion PLIC 只看到一個 source。 handler 必須 drain 整個 used ring，不能假設一次 IRQ 只有一筆。
處理期間同一來源再次產生事件 完成後若來源仍 pending，可再次被送達。 ACK 與 drain 順序要能處理合併、重複或晚到的 completion。
